# 创建 Catea Skill

Catea 的技能是纯 Markdown：放在 vault 的 `.catea/skills/<id>/SKILL.md`，启用后整段注入系统提示。技能只增加**做法和知识**，不增加工具，也不放宽审批。

方法论改编自 Anthropic 的 `anthropics/skills` 中 skill-creator（Apache-2.0），执行层按 Catea 的真实工具改写；原文里的 Python 评测回环、`claude -p`、浏览器评审页和 `.skill` 打包在这里都不存在，不要照做。

## 先问清意图

用户常常已经在让你做那件事了。如果当前对话里刚跑过一遍这个流程，先从历史里提取：用了哪些工具、按什么顺序、用户中途纠正过什么、输入输出的真实格式是什么。补齐缺的部分，然后**在动手写之前复述一遍**让用户确认。

要问清楚的四件事：这个技能要让 agent 做成什么、什么情况下该触发、期望输出长什么样、哪些是绝对不能碰的。

## 写 description

description 是唯一的触发依据，所有"什么时候用"都写在这里，不要塞进正文。模型天生倾向**欠触发**——技能明明有用却不用。所以描述要写得主动一点：除了说明它做什么，还要列出该用的信号，即使用户没有说出那个关键词。

不要写"一个强大的写作助手"。要写"用户修改中文草稿、润色段落、调整语气时使用，包括他说'这段读起来别扭'或'帮我顺一下'的时候"。

## 写正文

- 用祈使句，直接说做什么。
- 解释**为什么**重要，比堆一串"必须""MUST"有效。模型理解了理由才会在新情况下正确推广。
- 技能要通用，不要写死成只对当前这个例子成立。
- 边界写成禁止项，具体到路径和操作：不改 `raw/`、不碰隐藏目录、不批量重写无关笔记、不承诺本轮没有列出的工具。
- 不要把 persona 的说话风格搬进技能。人格管语气，技能管做事。
- 控制在 500 行以内。快到时加一层目录，把细节推到资源文件。

写完先放着，回头以陌生眼光读一遍再改。

## 分层加载

Catea 有三层，写技能时按层分配内容：

1. **name + description**：始终在上下文里，约百字。
2. **SKILL.md 正文**：启用后整段在上下文里，越省越好。
3. **资源文件**：只在需要时用 `skill_read` 读，单个不超过 48 KB。SKILL.md 本身同样受 48 KB 约束。

长材料放第 3 层，并在正文里写清"什么时候读哪个文件"。超过 300 行的资源要带目录。多领域技能按变体分文件（`references/aws.md`、`references/gcp.md`），只读相关的那份。

注意：`scripts/` 之类的目录在别的宿主里能执行，在 Catea 里不会。资源只是文本，技能不能靠附带脚本来"获得"能力。

## Principle of Lack of Surprise

技能内容不得包含恶意代码、绕过授权的手段、或会让用户意外的东西。如果向用户描述这个技能在做什么时他自己会觉得"这跟我说的不是一回事"，那就不要写。教人做误导性技能、外泄数据、越权访问的请求，不接。

## 落盘

用 `skill_create` 写入：`id`、`content`（完整 SKILL.md 正文）、可选 `resources`。写入前展示全文并等待用户确认；用户取消就停止，不要改用 `write`、`edit`、`obsidian_*` 或 shell 绕过——隐藏目录对这些工具本来就是封闭的。

`skill_create` 会强制校验，报错就按报错改，不要绕过：id 只能字母数字下划线连字符；frontmatter 的 `name` 必须与 id 完全一致；必须有非空 `description`；内置预设（`skill-creator`、`find-skill`）不可覆盖，要定制就换 id。

## 启用并验证

`.catea/` 对 agent 是隐藏的，你无法替用户改设置。告诉他两条路，别自作主张：设置面板 Skills 区打开开关是持久的，输入框 `/` 标签只带本轮。

然后**真的试一轮**：启用后跑一个有代表性的请求，看输出对不对，不对就回原文改。跳过验证不要说"技能已经可用"。

迭代时看真实记录，不看感觉：这次哪里判断错了、哪些指令实际不起作用、什么内容反复出现在输出里本该抽成规则、有没有哪条规则只是把结果挪去别处出错。一次改多处，但每轮只保留真正让输出变好的改动——为个例加的特例是复杂度，不是改进。
